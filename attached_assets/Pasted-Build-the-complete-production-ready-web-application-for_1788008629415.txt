8. SQL QUERY TERMINAL
==================================================

This is one of the most important parts of the application.

Create a professional SQL editor.

Participants must eventually be able to:

1. Write SQL.
2. Click RUN QUERY.
3. Send the query to FastAPI.
4. Backend validates the query.
5. Backend executes the query against the designated investigation database.
6. Return safe results.
7. Display results in a table.

The UI should resemble a professional coding/query environment.

Include:

- SQL editor
- syntax highlighting
- Run Query button
- Clear button
- query execution state
- results table
- error display
- row count
- execution time if appropriate

IMPORTANT:

RUN QUERY and SUBMIT ANSWER are completely separate actions.

Running queries does NOT cause an answer penalty.

Participants should eventually be able to run many queries.

==================================================
9. SQL SECURITY
==================================================

Do NOT allow participant queries to freely manipulate the production Supabase database.

Create a safe query execution architecture.

Participants must NOT be able to execute:

DROP
DELETE
UPDATE
INSERT
ALTER
TRUNCATE
CREATE
GRANT
REVOKE

or equivalent destructive operations.

Prevent access to:

- PostgreSQL system tables
- Supabase internal tables
- application management tables
- secrets
- credentials
- answer keys
- other participants' sessions
- administrative data

Implement server-side query validation.

Do NOT rely on frontend restrictions.

Implement:

- statement timeout
- result row limits
- query length limits
- safe error handling
- connection pooling
- appropriate rate limiting
- backend-only database credentials

Prefer a dedicated read-only investigation database role/schema for participant queries.

==================================================
